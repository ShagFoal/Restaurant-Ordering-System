# Egor — материалы для общего отчёта

Этот фрагмент описывает часть Student 3: Adapter, Facade, консольную интеграцию и настройку сборки. Он предназначен для включения в общий командный отчёт. Разделы Askhat и Danila, титульный лист, Introduction, Conclusion и Further Work готовятся совместно с их авторами.

## Задача и границы работы

В Restaurant Ordering System пользователь выбирает блюда, скидку и подтверждает заказ. Моя часть подключает имитацию старой платежной системы, объединяет компоненты через Facade и предоставляет консольный интерфейс.

Factory Method и Builder реализовал Askhat; Strategy и Observer — Danila. Их готовые классы используются через согласованные контракты. Логика этих классов и их пакеты в данной части не изменяются.

## Adapter

Приложению нужен метод `boolean pay(int amount)`. Старая платежная система предоставляет другой метод: `String makePayment(String amount)`. Различаются и тип суммы, и тип результата.

`PaymentProcessor` — Target, `LegacyPaymentSystem` — Adaptee, `LegacyPaymentAdapter` — Adapter. Клиентом выступает `OrderFacade`, который зависит только от `PaymentProcessor`.

Ключевой фрагмент адаптера:

```java
String result = legacyPaymentSystem.makePayment(String.valueOf(amount));
return "SUCCESS".equals(result);
```

При сумме `4500` Legacy получает строку `"4500"`. Ответ `"SUCCESS"` преобразуется в `true`, `"FAILED"` — в `false`. Ноль, отрицательные значения и некорректные строки отклоняются. Обязательная ссылка на Legacy проверяется в конструкторе Adapter.

Adapter содержит объект старой системы и делегирует ему вызов. Это Object Adapter. Если заменить строковый API Legacy на `pay(int)`, исчезнет несовместимость, которую должен устранять паттерн.

Оплата является имитацией: программа не обращается к банку, не использует ключи доступа и не списывает деньги.

## Facade

`OrderFacade` предоставляет три операции:

| Метод | Что делает | Кому делегирует |
|---|---|---|
| `createOrder(name, meals, comment)` | Собирает заказ и подключает подписчиков | `OrderBuilder`, `Order.addObserver()` |
| `calculateTotal(order)` | Возвращает сумму после скидки | `DiscountStrategy.calculateTotal()` |
| `checkout(order)` | Проверяет статус, оплачивает и запускает обработку | `PaymentProcessor`, `Order.setStatus()` |

Facade получает платежный интерфейс, стратегию и список подписчиков через конструктор. Ссылки на зависимости неизменяемы, список подписчиков копируется. `null` вместо обязательных зависимостей отклоняется.

Создание заказа и предпросмотр не вызывают оплату. `checkout()` разрешен только для `CREATED`. При отказе платежа он возвращает `false` и сохраняет исходный статус. При успехе выполняются переходы `CREATED → PAID → PREPARING → READY`.

Уведомления отправляет `Order`; Facade не вызывает callbacks вручную. Повторный checkout обработанного заказа приводит к `IllegalStateException` до платежного вызова. Это предотвращает повторное списание в рамках предусмотренного однопоточного сценария.

Facade упрощает использование подсистемы, сохраняя правила в соответствующих компонентах. Расчет скидки находится в Strategy, создание заказа — в Builder, преобразование платежного API — в Adapter, уведомления — в Observer.

## Main и взаимодействие паттернов

`Main` отвечает за ввод и вывод. Он создает конкретные компоненты, передает зависимости в Facade и запускает оформление только после `y`. Ответ `n` или конец ввода завершают программу без платежа. Неправильное имя или пункт меню вызывают повтор текущего ввода.

В успешном сценарии пользователь выбирает Pizza и Burger. Factory Method создает блюда, Builder собирает заказ на `5000 KZT`, Strategy дает `4500 KZT` при Student Discount. Facade вызывает оплату через Adapter и меняет статус заказа. Observer автоматически уведомляет покупателя и кухню: по три сообщения каждому.

Цены меню читаются из `Meal`, название скидки — из `DiscountStrategy`. В `Main` нет формулы скидки, прямого вызова Legacy или ручной последовательности смены статусов.

## Качество кода

| Принцип | Пример в моей части |
|---|---|
| SRP | Main ведет диалог, Adapter переводит интерфейсы, Facade управляет последовательностью оформления |
| OCP | Другой платежный компонент или стратегия передаются через тот же конструктор без изменения checkout |
| LSP | Facade работает с реализациями PaymentProcessor по одному контракту; обычный отказ выражается `false` |
| ISP | PaymentProcessor содержит только необходимый клиенту метод `pay(int)` |
| DIP | Facade зависит от PaymentProcessor и DiscountStrategy; конкретные реализации выбирает Main |
| DRY | Предпросмотр и checkout используют один calculateTotal; Main не дублирует цены или формулу скидки |
| KISS | Один заказ, стандартная Java, синхронная обработка, без базы данных, сети и дополнительных слоев |

В Main выделены небольшие методы для имени, блюд, скидки, числового ввода, предпросмотра и подтверждения. Все строки читаются через один Scanner с `nextLine()`, поэтому после числового выбора не остается необработанного перевода строки.

## Проверка

Проверено 13 ноября 2026 года. Сборка Maven и строгая компиляция `javac --release 17 -Xlint:all -Werror` прошли. Классы имеют версию байткода 61. Запуски выполнены на установленном JDK 25; отдельный запуск всей интегрированной версии на JDK 17 пока не выполнялся.

| Проверка | Фактический результат |
|---|---|
| Pizza + Burger, Student Discount | Subtotal 5000, total 4500, один платеж, READY, шесть уведомлений |
| Те же блюда без скидки | Total 5000, пустой комментарий допустим |
| Две Pizza и Burger | Subtotal 8000, total 7200; повторная позиция сохраняется |
| Отказ `n` | Нет платежа и статусных уведомлений |
| Пустое имя, текст и неверные номера меню | Повтор ввода на нужном шаге, выбранные блюда сохраняются |
| Кириллица, пробелы и `Y` / `N` | Данные нормализуются, подтверждение не зависит от регистра |
| Конец ввода до подтверждения | Во всех 11 проверенных точках программа завершается без платежа и stack trace |
| Adapter: 4500, 0, -1 | Соответственно true, false, false |
| Legacy: null, текст, число вне int | FAILED |
| Facade с платежным компонентом, возвращающим false | Заказ остается CREATED, уведомлений нет |
| Повторный checkout успешного заказа | IllegalStateException, нового платежа нет |

Всего проверено 19 запусков CLI и отдельные API-сценарии. Проверки выполнялись на настоящих классах проекта; тестовые классы и тестовые зависимости в репозиторий не добавлялись.

## Как повторить демонстрацию

Для сборки нужны JDK 17 или новее и Maven. Из корня репозитория:

```text
mvn clean package
java -cp target/classes org.example.restaurant.Main
```

В текущей рабочей папке VS Code также настроена конфигурация `Restaurant Ordering System`: выбрать её в разделе «Запуск и отладка» и нажать F5. Настройки редактора находятся вне репозитория; после нового клонирования можно использовать команды выше.

Успешный сценарий: `Egor` → `1` → `2` → `0` → `No onions` → `2` → `y`. Каждое значение подтверждается Enter. Ожидаемый результат — `4500 KZT`, один успешный платеж, шесть уведомлений и сообщение `Order is ready. Payment successful.`
